How to read this document

Sections 1 to 3 describe the business case and are written for every reader. Sections 4 to 9 describe the proposed technical solution. Sections 10 to 14 cover security, quality and operations, and are of most interest to architects and DevOps engineers. Sections 15 to 17 cover the delivery plan, risks and next steps.

1Executive summary

We propose to build the Food Delivery Platform as a set of small, independently deployable services that communicate through a central API gateway and an event backbone. Customers order food from local restaurants, restaurants manage their menus and orders, delivery partners carry orders to the customer's door, and platform administrators supervise the whole marketplace.

A microservices architecture is proposed because the platform has several clearly separate business domains (users, restaurants, menus, orders, payments, deliveries, notifications, search) that change at different speeds, carry different loads and have different reliability needs. Splitting them lets each domain be built, tested, scaled and released on its own, and keeps a failure in one area (for example the search index) from stopping the others (for example checkout).

Key features of the proposal

  • One entry point. All traffic enters through an API gateway that routes requests, limits abusive traffic and protects services that are temporarily unavailable.
  • Event-driven integration. Services publish business events (an order was created, a payment succeeded, a delivery was picked up) to Apache Kafka. Other services react to those events instead of calling each other, which keeps them loosely coupled.
  • Reliable by design. A transactional outbox guarantees that a change and its event are saved together; a choreographed saga coordinates checkout, payment, refunds and delivery without a central coordinator.
  • Fast discovery. Restaurant and dish search runs on Elasticsearch, kept up to date from events, with typo-tolerant matching and filters.
  • Built for operations. Metrics, logs and distributed traces are part of every service from the start, with ready-made dashboards.
  • Quality gates. Unit, integration and end-to-end tests, architecture rules and static analysis run on every build.
  • AI assistance. A role-aware conversational assistant (Spring AI with a locally hosted language model) answers questions about orders, menus and deliveries and can prepare actions that a person confirms.

2Business context and objectives

2.1 Context

Online food delivery connects three groups of people who all depend on the same order: the customer who pays, the restaurant that cooks, and the rider who delivers. Each step has to be visible to the others in near real time, money must never be taken twice or lost, and the platform operator needs to supervise restaurants, riders, refunds and disputes. Demand is also uneven: lunch and dinner peaks can multiply traffic for browsing, checkout and tracking within minutes.

2.2 Objectives

ObjectiveHow the proposal meets it
Independent evolution of business areasOne service per domain with its own database and release cycle; contracts between services are versioned events and REST APIs.
Reliable money handlingIdempotent payment and refund APIs, verified payment-provider callbacks, automatic refunds for cancelled orders, and an immutable audit trail.
Real-time experienceEvent-driven status changes pushed to browsers over WebSocket; live delivery tracking on a map.
Scalability at peak timesStateless services that scale horizontally; Kafka partitions spread event processing; Redis caches hot reads.
Graceful degradationTimeouts, retries, circuit breakers and fallbacks so that one slow or failed service does not take the platform down.
Operational visibilityMetrics, centralised logs and distributed tracing for every request, from the gateway through every service and event.
MaintainabilityConsistent project structure, automated quality gates and documentation per service.

2.3 Success criteria

  • A customer can find a restaurant, order, pay, track and receive an order end to end through the web application.
  • Restaurants, riders and administrators each have a working area for their daily tasks.
  • Every business flow is covered by automated end-to-end tests that run against the deployed platform.
  • The loss or slowness of one non-critical service is visible on dashboards and does not stop checkout.

4Proposed solution architecture

The platform is organised in four layers: a single web application; an API gateway; independent domain services; and shared infrastructure (event backbone, databases, cache, search, observability). The figure below shows the proposed components and how they connect.

4.1 Architecture principles

PrincipleWhat it means in practice
Database per serviceEach service owns its tables; no service reads another service's database. Data needed elsewhere is shared through APIs or events.
Single entry pointBrowsers talk only to the API gateway, which hides the internal topology and applies cross-cutting protection.
Events for cross-domain changeWhen something important happens, the owning service publishes an event; interested services react. Services do not instruct each other.
Synchronous calls only when neededA direct REST call is used only when a fresh answer is required to complete a request (for example, price check at checkout) and is always guarded by timeouts and circuit breakers.
At-least-once delivery, applied onceEvents may be delivered more than once; consumers detect and skip repeats so the effect happens once.
Stateless servicesNo session state in memory; any instance can serve any request, so services scale horizontally.
Observable by defaultEvery request carries a request id and a trace context through REST calls and events.
Contracts firstREST APIs are versioned (/api/v1) and documented with OpenAPI; events are Avro schemas checked for compatibility by a schema registry.

4.2 Why microservices

A single large application would be simpler to start but would force every change through one release, one database and one scaling unit. The proposed split follows business capabilities, so each team or developer can work on one domain with a small, understandable code base. The added complexity of distribution (network failures, eventual consistency, operations) is addressed explicitly by the communication patterns in section 6, the resilience measures in section 11 and the observability in section 12.

5.1 Shared libraries

One shared library, event-contracts, holds the Avro schemas of every business event and the topic names. It is versioned and installed like any other dependency; it contains no business logic, so services remain independent.

5.2 Why these boundaries

  • Order and payment are separate because payments have their own provider integration, security requirements and reconciliation, and must never be charged twice by a retried order request.
  • Delivery and delivery partner are separate: who a partner is (profile, suspension) changes rarely, while dispatch (who is free, who gets which order) must happen inside one database transaction to guarantee that no partner receives two deliveries.
  • Search is a read model: it owns no business data; it is rebuilt from events and can be replaced or re-indexed without touching the source services.
  • Admin owns no business data: it composes figures from the services that own them and keeps a copy of every audit record for one platform-wide audit view.

6Communication patterns

6.1 Client to platform: REST through the gateway

  • Versioned JSON APIs under /api/v1; administrator APIs under /api/v1/admin.
  • Errors follow RFC 9457 (ProblemDetail), with business messages that are safe to show to users.
  • Lists are paginated on the server (page, size, sort; at most 100 per page).
  • Every response carries an X-Request-Id that follows the request through all services and events.
  • State-changing operations that must not be repeated (placing an order, paying, refunding) take an Idempotency-Key: a retried request returns the original result instead of acting twice.

6.2 Service to service: synchronous REST, guarded

A service calls another directly only when it needs a fresh answer to complete the current request: for example, checkout confirms prices with the catalog and reserves a coupon with the promotion service. Every such call has a timeout, a retry only when the connection itself failed, a circuit breaker per target service and a bulkhead limiting concurrent calls (details in section 11).

6.3 Asynchronous events: Kafka with Avro

When a service changes something other services care about, it publishes an event. Events are defined as Avro schemas and registered in Confluent Schema Registry, which rejects schema changes that would break existing consumers. Each topic has three partitions; events are keyed by entity (for example the order id), so all events of one order are processed in order. A consumer that cannot process an event retries it, then moves it to a dead-letter topic so the stream is never blocked.

6.4 Transactional outbox and idempotent consumers

Writing to the database and publishing to Kafka are two separate systems; doing both in a request risks saving a change without its event, or the other way round. The outbox pattern removes that risk: the service writes the event into its own outbox_events table in the same database transaction as the change, and a relay publishes it to Kafka shortly afterwards. If Kafka is unavailable, requests still succeed and events wait. Consumers record each processed event id, so an event delivered twice is applied once.

6.5 Saga choreography for checkout

An order spans several services (order, payment, restaurant, delivery, promotion, notification). Instead of a central coordinator, each service reacts to the previous step's event: order created, payment succeeded, order placed, food ready, delivery assigned, picked up, delivered. Failures trigger compensating steps: a cancelled paid order is refunded automatically, a coupon use is given back, a delivery is cancelled and its partner freed, and an unpaid order is cancelled after a time limit.

6.6 Real-time updates

Browsers keep one WebSocket connection through the gateway. The notification service turns business events into small live messages (order moved to preparing, delivery picked up, new support message), so pages update without polling. Pages fall back to periodic refresh when the connection is lost.

6.7 Read models for search

The search service builds its Elasticsearch indexes from restaurant and catalog events (a CQRS-style read model). MySQL remains the source of truth; a consistency check can detect and repair any drift, and indexes can be rebuilt by replaying the current state.

7.1 Local copies instead of chatty calls

Where a service needs another's data frequently, it keeps a small local copy updated from events: the catalog keeps a snapshot of each restaurant, payment keeps the orders awaiting payment, delivery keeps pickup and drop-off addresses. This keeps menus working while the restaurant service is down, payments possible while the order service restarts, and started deliveries completable during short outages.

7.2 Consistency model

Inside a service, data is strongly consistent. Across services the platform is eventually consistent: for example, an order moves to "placed" a moment (usually well under a second) after the payment succeeds. Concurrent conflicting changes are detected by optimistic locking and rejected with a clear "please retry" answer.

7.3 Auditing

Every administrator action (approve a restaurant, block a dish, refund a payment, reassign a delivery) is written to an immutable audit table in the same transaction as the change, with who, when, why and the request id. A copy is sent to the admin service for a single platform-wide audit view.

Resource planning

Running every service, the full observability stack and the language model on a single developer workstation needs more than 16 GB of memory for containers. The proposed development set-up therefore runs the infrastructure in Docker and the services as local processes, with the observability stack started only when needed. Production environments size each component separately (section 14).

10Security architecture

10.1 Identity and access

Security is delivered in two steps so that functional work is not blocked:

  1. Development phases (interim). Users sign in with e-mail and password, verified by the user service (passwords stored as BCrypt hashes). The web application then sends the signed-in user's id and role in request headers. This is suitable only for development and testing environments that are not exposed to the internet.
  2. Final phase: token-based security (proposed). Spring Security with JSON Web Tokens: the user service (or an identity provider) issues signed access tokens; the API gateway validates every token and passes the verified identity to the services; services reject requests that did not come through the gateway. Refresh tokens, token expiry and sign-out are included. Because identity is resolved in one place per service, this change does not alter business code.

10.2 Authorisation

Role-based access control with four roles: CUSTOMER, RESTAURANT_ADMIN, DELIVERY_PARTNER and PLATFORM_ADMIN. Every service checks the role for each endpoint and enforces ownership in its own business logic (an owner sees only their restaurant's orders, a partner only their own deliveries, a customer only their own orders). Nobody can register as an administrator; the first administrator is created from protected configuration.

10.3 Protection of data and transactions

  • Transport: HTTPS (TLS) at the edge in every non-local environment; internal traffic on a private network.
  • Payments: card details never touch the platform; the provider's hosted checkout handles them. Payment callbacks are accepted only after their signature is verified (HMAC) and the provider confirms the captured amount.
  • Idempotency: orders, payments and refunds accept an idempotency key so that a retried request cannot charge or refund twice.
  • Secrets: passwords and keys come from environment configuration (a secrets manager in production), never from source code.
  • Input validation: every request body is validated; errors never expose stack traces or internal details.
  • Abuse protection: per-client rate limits at the gateway, stricter limits for sign-in and registration.
  • Auditing: immutable audit records of every administrator action, with the reason given.

10.4 AI assistant safeguards

  • The assistant's identity comes from the verified session, never from what the user types or what the model produces.
  • Each role is offered only its own tools; the business services check permissions again on every call.
  • The model cannot change anything by itself: it can only prepare an action (place or cancel an order, accept an order, mark a delivery) that the user must confirm with a button.
  • The language model runs locally, so conversation data is not sent to third-party AI services.

The web application is built per environment from its own configuration file (gateway address, feature flags), so the same code moves through every stage.

14.2 Packaging

  • Every service has a multi-stage Dockerfile: the build stage compiles and packages; the runtime stage uses a slim Java runtime, a layered JAR for fast rebuilds, and runs as a non-root user.
  • Docker Compose describes the infrastructure and, through profiles, optional groups (services, AI, change data capture, code quality). A script starts the services locally for development.
  • Database schemas migrate automatically at service start-up (Flyway), forward-only and backward compatible.

14.3 Proposed production topology

Recommendation (to be confirmed with the client's hosting choice)
  • Orchestration: a managed Kubernetes service (for example AKS, EKS or GKE) with one deployment per service, at least two replicas each, readiness and liveness probes on the existing health endpoints, and horizontal autoscaling on CPU and request rate.
  • Edge: an ingress controller or cloud load balancer terminating TLS in front of the API gateway; a CDN for the web application's static files.
  • Data services: managed MySQL with automated backups and point-in-time recovery; managed Kafka with Schema Registry; managed Redis; managed Elasticsearch (or OpenSearch).
  • AI model: a GPU node pool or a dedicated model host for responsive assistant answers.
  • Secrets and configuration: a secrets manager (for example Azure Key Vault, AWS Secrets Manager or HashiCorp Vault) injected as environment variables.
  • Observability: the same Prometheus, Grafana, Loki and Tempo stack (self-hosted or a managed Grafana offering) with alert rules for errors, latency, consumer lag and outbox backlog.

14.4 Proposed CI/CD pipeline

  1. Build and test each changed service: unit, slice and integration tests, architecture rules, Checkstyle, SpotBugs, coverage.
  2. Quality gate in SonarQube; the pipeline stops on failure.
  3. Container image built once, tagged with the commit, scanned for vulnerabilities and pushed to a registry.
  4. Deploy to UAT automatically; run the end-to-end suite against it.
  5. Promote the same image to pre-production and production after approval, with rolling or blue-green deployment and automatic rollback when health checks fail.

17Assumptions and next steps

17.1 Assumptions

  • The client provides payment provider accounts (test and live keys) and a mail and SMS provider for production.
  • The hosting platform (cloud provider or on-premises) is decided before the pre-production environment is built.
  • The web application is the primary client; native mobile apps can reuse the same APIs later.
  • Real-time rider GPS requires a rider mobile application or device integration, delivered as a follow-up.
